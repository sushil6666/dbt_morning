A running collection of gotchas, tips, and lessons learned while working with this project.

## 1. Jinja Comments vs SQL Comments in dbt Config Blocks

### Problem

Using a SQL comment (`--`) to "disable" a `config()` block does **not** work as expected:

```sql
--{{ config(materialized='view') }}
```

This looks commented out, but dbt **still materializes the model as a view**.

### Why

dbt uses Jinja to render the SQL template **before** the SQL engine ever sees it. Jinja processes `{{ config(materialized='view') }}` first — the `config()` call executes and sets the materialization — then renders the tag to an empty string. The `--` only comments out that empty string in the final SQL, not the Jinja execution itself.

Priority order when the in-file `config()` runs (even disguised behind `--`):
```
in-file config() > dbt_project.yml > dbt defaults
```

### Fix — Use a Jinja Comment Instead

```sql
{# {{ config(materialized='view') }} #}
```

Jinja strips `{# ... #}` blocks **before** evaluating anything inside them. The `config()` call never runs, so `dbt_project.yml` controls the materialization as intended.

### Summary

| Syntax | Jinja executes? | Effective? |
|--------|----------------|------------|
| `--{{ config(...) }}` | Yes | config() still applies |
| `{# {{ config(...) }} #}` | No | config() is fully ignored |

### Rule of Thumb

> Any time you want to comment out Jinja logic in a dbt model, use `{# ... #}`, never `--`.

## 2. Source Freshness & `source_status:fresher+` Selector

### What It Does

`source_status:fresher+` selects all models downstream of sources whose `max_loaded_at` timestamp is more recent in the **current** freshness check than in a **prior saved state**. This lets you build only what's actually new, rather than rebuilding everything.

### How It Works

dbt compares two `sources.json` files:
- **Current** — freshness just checked, written to `target/sources.json`
- **Prior state** — artifacts from a previous run, passed via `--state`

A source is "fresher" if its `max_loaded_at` in the current run is later than in the prior state.

### Step-by-Step

**Step 1 — Run source freshness to generate `target/sources.json`:**
```bash
dbt source freshness
```

**Step 2 — Build only models downstream of fresher sources:**
```bash
dbt build --select source_status:fresher+ --state ./prev-state
```

`./prev-state` must contain a `sources.json` from a **previous** run (not `manifest.json` — that's used by `state:modified+`, not `source_status:fresher+`).

### Full Local Workflow (simulating new data)

```bash
# 1. Save current state as the "prior" baseline
mkdir -p prev-state && cp target/sources.json prev-state/

# 2. New data loads into Snowflake source tables (happens externally)

# 3. Refresh freshness to update target/sources.json
dbt source freshness

# 4. Build only what changed
dbt build --select source_status:fresher+ --state ./prev-state
```

### CI/CD Workflow

In CI, `prev-state/` is populated by downloading production artifacts before the run:

```bash
# Download last prod sources.json into prev-state/
# (from dbt Cloud, S3, or equivalent artifact store)

dbt source freshness
dbt build --select source_status:fresher+ --state ./prev-state
```

### Common Gotcha — "Nothing to do"

```
warning: dbt1092: The selection criterion 'source_status:fresher+' does not match any enabled nodes
```

This happens when:
| Cause | Fix |
|-------|-----|
| `--state` points to the same `target/` folder | Point to a **separate** prior-state directory |
| No new data has loaded since the prior state | Expected — nothing is fresher, nothing runs |
| `dbt source freshness` was never run (no `sources.json`) | Run Step 1 first |

### Rule of Thumb

> `--state` must point to artifacts from a **different, earlier run**. Comparing `target/` against itself always yields zero fresher sources.

## 3. dbt Artifacts — What They Are and When to Use Them

dbt writes a set of JSON files to `target/` after each run. These **artifacts** are the foundation for slim CI, WAP, observability, and state-based selection.

### The Four Core Artifacts

| File | Generated by | Contains |
|------|-------------|----------|
| `manifest.json` | compile / run / build / test | Full project graph: models, tests, sources, macros, node configs |
| `run_results.json` | run / build / test / seed | Execution results, timing, row counts, status per node |
| `catalog.json` | `dbt docs generate` | Column-level metadata fetched from the warehouse |
| `sources.json` | `dbt source freshness` | `max_loaded_at` per source, used for freshness comparison |

---

### Use Case 1 — Slim CI (`state:modified+`)

Compare a PR's `manifest.json` against the last production manifest to build only what changed.

```bash
# In CI: download prod manifest into ./production-manifest/
dbt build --select "state:modified+" --defer --state ./production-manifest/
```

- `state:modified+` — nodes whose definition changed plus all downstream dependents
- `--defer` — for unmodified upstream nodes, resolve refs against the prod schema instead of rebuilding them
- **This project**: uploaded after every successful main push, retained 90 days (see `ci.yml`)

**Why it matters:** A PR touching one staging model doesn't rebuild the entire project — only that model and its children run.

---

### Use Case 2 — Source Freshness Gating (`source_status:fresher+`)

Use `sources.json` to build only models downstream of sources that received new data since the last run. Covered in detail in **Section 2** above.

---

### Use Case 3 — WAP (Write-Audit-Publish) via `manifest.json`

The CD pipeline uses the manifest to drive the WAP pattern:

1. **Write** — build models into a `_candidate` schema (audit copy)
2. **Audit** — run tests against `_candidate`; `run_results.json` captures pass/fail
3. **Publish** — if audit passes, `swap_schemas` atomically renames `_candidate` → prod

`run_results.json` is the gate: if any test status is `fail` or `error`, the publish step is skipped.

---

### Use Case 4 — Observability & Elementary

Elementary reads `run_results.json` and `manifest.json` after each run to populate its own dbt models (`elementary_test_results`, `model_run_results`, etc.). This powers dashboards and anomaly detection without any extra instrumentation.

```bash
edr report   # reads Elementary's models, which were fed by your artifacts
```

---

### Use Case 5 — `dbt docs` and the Catalog

`catalog.json` enriches the docs site with live column names, types, and row counts fetched from Snowflake.

```bash
dbt compile --write-catalog   # writes catalog.json (dbt-fusion compatible)
dbt docs serve                # serves manifest + catalog together
```

> **Note:** `dbt docs generate` is not supported in dbt-fusion 2.0. Use `dbt compile --write-catalog` instead to produce `catalog.json`.

Without `catalog.json`, the docs site still works but shows no column-level warehouse metadata.

---

### Artifact Cheat Sheet

| Goal | Artifact needed | Command that produces it |
|------|----------------|--------------------------|
| Slim CI / state comparison | `manifest.json` | any `dbt build/run/compile` |
| Source freshness gating | `sources.json` | `dbt source freshness` |
| WAP audit gate | `run_results.json` | `dbt build/test` |
| Docs with column metadata | `catalog.json` | `dbt compile --write-catalog` |
| Elementary dashboards | `manifest.json` + `run_results.json` | `dbt build` |

### Rule of Thumb

> Artifacts are only as fresh as the last run that produced them. Always store production artifacts externally (S3, GH Actions cache, dbt Cloud) so CI and CD can compare against a known-good baseline, not against stale local files.

## 4. pre_hook vs post_hook — When to Use Each

### Rule of Thumb

| Hook | Use when |
|------|----------|
| `pre_hook` | The table does **not** need to exist yet — session params, schema creation, audit log insert |
| `post_hook` | The table **must** already exist — DDL constraints, row count capture, GRANT, audit log update |

Using `ALTER TABLE … ADD PRIMARY KEY` in a `pre_hook` will fail on the first build because the table hasn't been created yet. That's why `apply_constraints()` is always a `post_hook`.

## 5. `feature_flag()` Macro — The `{{ }}` vs `return()` Gotcha

### Problem

```sql
{% macro feature_flag(flag_name, default=false) %}
    {{ var(flag_name, default) | as_bool }}
{% endmacro %}
```

`{{ False | as_bool }}` renders as the **string** `"False"`. In Jinja,
`{% if "False" %}` is **truthy** (non-empty string), so the flag can never
be switched off — it is always active regardless of the var value.

### Fix — Use `return()`

```sql
{% macro feature_flag(flag_name, default=false) %}
    {{ return(var(flag_name, default) | as_bool) }}
{% endmacro %}
```

`return()` hands back the actual Python boolean, not its string representation.
`{% if True %}` / `{% if False %}` then behaves correctly.

### Rule of Thumb

> Any time a macro is used inside `{% if macro_call() %}`, the macro must use
> `return()` to yield the actual value — not `{{ }}` which always renders a
> non-empty string.

## 6. Snowflake Multi-Statement API Calls in Hooks

### Problem

Snowflake rejects multi-statement API calls by default. A hook macro that
emits more than one SQL statement in a single string will fail:

```sql
-- This FAILS — two statements in one API call
{% macro bad_macro() %}
    CREATE SCHEMA IF NOT EXISTS MY_DB.AUDIT;
    INSERT INTO MY_DB.AUDIT.LOG ...;
{% endmacro %}
```

### Fix — Wrap in `EXECUTE IMMEDIATE $$ BEGIN…END; $$`

```sql
{% macro good_macro() %}
EXECUTE IMMEDIATE $$
BEGIN
    CREATE SCHEMA IF NOT EXISTS MY_DB.AUDIT;
    INSERT INTO MY_DB.AUDIT.LOG ...;
END;
$$
{% endmacro %}
```

This sends exactly **one** SQL call to Snowflake regardless of how many
statements are inside the block. Jinja resolves template variables (like
`{{ invocation_id }}`) before the string is sent, so they work normally inside
the `$$` block.

### When This Does Not Apply

Each element of a `pre_hook` **list** is a separate API call, so single-statement
strings in a list are fine without `EXECUTE IMMEDIATE`:

```sql
pre_hook=[
    "ALTER SESSION SET TIMEZONE = 'UTC'",   -- one call
    "ALTER SESSION SET WEEK_START = 1",      -- one call
    "ALTER SESSION SET USE_CACHED_RESULT = FALSE"  -- one call
]
```
